# Local Root with Unbound

Unbound supports a local copy of the root zone using an **authority zone** (`auth-zone`).

An authority zone can be loaded from a zone file and can also be maintained using AXFR and IXFR. For a local root, Unbound uses:

```text
auth-zone:
    name: "."
```

with:

```text
for-upstream: yes
for-downstream: no
```

This means that Unbound uses the locally maintained root data when performing recursion, but does not act as a public authoritative root server for downstream clients. This matches the design described by RFC 8806.

# Check the current configuration

First determine where Unbound gets its root hints:

```bash
grep -R -n 'root-hints' /etc/unbound/
```

You may see something similar to:

```text
root-hints: "/var/lib/unbound/root.hints"
```

Unbound can also use built-in root hints if no `root-hints` file is configured.

Root hints and a local root zone are not the same thing.

Root hints tell Unbound where the root servers are.

Our new `auth-zone` will give Unbound an actual copy of the root zone.

# Add the local root authority zone

Create a configuration file:

```bash
nano /etc/unbound/unbound.conf.d/localroot.conf
```

Add:

```text
auth-zone:
    name: "."
    master: "192.0.32.132"
    master: "192.0.47.132"
    fallback-enabled: no
    for-downstream: no
    for-upstream: yes
    zonefile: "/var/lib/unbound/root.zone"
```

The two addresses above are ICANN root-zone transfer servers documented as sources for the root zone in RFC 8806.

We deliberately use IP addresses rather than host names.

At the beginning of a root-zone bootstrap process, relying on DNS to resolve the name of the server from which the root zone is obtained can create an undesirable circular dependency. Current Unbound documentation also recommends avoiding such name-lookup dependencies for authority-zone sources.

# What do these settings mean?

The configuration is worth understanding rather than simply copying.

```text
name: "."
```

means that the authority zone is the DNS root zone.

```text
master: "192.0.32.132"
master: "192.0.47.132"
```

specifies the servers from which Unbound can obtain the zone using AXFR or IXFR.

```text
for-upstream: yes
```

means that the root data is used while Unbound performs recursive resolution.

```text
for-downstream: no
```

means that Unbound does not behave as a public authoritative root server for clients.

This distinction is important for RFC 8806.

```text
fallback-enabled: no
```

means that, for this lab, Unbound will not silently fall back to normal Internet root resolution if the local authority zone is unavailable.

That makes the behavior easier to observe.

In a production deployment you should evaluate the desired failure mode carefully.

# Check the configuration

Run:

```bash
unbound-checkconf
```

The command should report no errors.

# Restart Unbound

Restart the service:

```bash
systemctl restart unbound
```

Check the service:

```bash
systemctl status unbound
```

If there is a problem:

```bash
journalctl -u unbound --no-pager -n 100
```

# Check the authority zone

Unbound has a control command specifically for listing authority zones:

```bash
unbound-control list_auth_zones
```

You should see the root zone:

```text
.
```

The output includes the status and current serial number of configured authority zones.

# Check the root-zone transfer

You can explicitly request an authority-zone transfer:

```bash
unbound-control auth_zone_transfer .
```

This starts the authority-zone transfer procedure.

Then check the status again:

```bash
unbound-control list_auth_zones
```

Unbound supports AXFR and IXFR for authority zones and stores the updated zone in the configured zone file.

# Check the zone file

Look for:

```bash
ls -lh /var/lib/unbound/root.zone
```

The file should exist after a successful transfer.

You can inspect the beginning of the zone:

```bash
head -30 /var/lib/unbound/root.zone
```

You should see the root SOA and other root-zone records.

Do not edit this file manually.

It is maintained by Unbound.

# Query the local root

Ask Unbound for the root SOA:

```bash
dig @127.0.0.1 . SOA
```

Then query the root NS records:

```bash
dig @127.0.0.1 . NS
```

Now ask for a TLD delegation:

```bash
dig @127.0.0.1 com NS
```

Finally perform a normal lookup:

```bash
dig @127.0.0.1 icann.org A
```

The final answer should look normal.

The important difference is that root-zone information is now taken from the local `auth-zone`.

# Compare the local root with a remote root

Query the local root:

```bash
dig @127.0.0.1 . SOA
```

Then query a public root server:

```bash
dig @198.41.0.4 . SOA
```

Compare the SOA serial numbers.

They should identify the same root-zone version.

# Check DNSSEC

The root zone is signed.

Ask Unbound for the root DNSKEY records:

```bash
dig @127.0.0.1 . DNSKEY +dnssec
```

Also check a delegation:

```bash
dig @127.0.0.1 com NS +dnssec
```

Because the authority zone is configured with:

```text
for-upstream: yes
for-downstream: no
```

Unbound uses the authority-zone data as upstream data and performs DNSSEC validation before using it for recursive responses. The Unbound documentation explicitly describes this behavior for authority zones.

# Test persistence

Unbound writes updated authority-zone data to the configured zone file.

Restart Unbound:

```bash
systemctl restart unbound
```

Then:

```bash
unbound-control list_auth_zones
```

and:

```bash
dig @127.0.0.1 . SOA
```

The local root should still be available.

# Test an update

The root zone changes over time, so a local root implementation must update itself.

Check the current status:

```bash
unbound-control list_auth_zones
```

Then ask Unbound to check for an updated version:

```bash
unbound-control auth_zone_transfer .
```

Check the serial again:

```bash
unbound-control list_auth_zones
```

Unbound uses the SOA timers and AXFR/IXFR to keep authority zones up to date.

# Why is for-downstream disabled?

It may seem strange to configure an authority zone and then explicitly disable:

```text
for-downstream: no
```

The reason is architectural.

This machine is primarily a recursive resolver.

The root zone is being kept locally so that the resolver can use it.

It is not intended to become an authoritative root server for the rest of the lab.

RFC 8806 requires the local root service to be restricted so that other resolvers cannot use it.

# Observe the local-root behavior

You can inspect Unbound statistics:

```bash
unbound-control stats_noreset | grep authzone
```

Recent Unbound versions expose counters for queries answered from authority-zone data.

This gives you another way to see that the local authority data is actually being used.

# Optional packet-capture experiment

To understand the difference from ordinary root hints, capture DNS traffic:

```bash
tcpdump -n port 53
```

Generate DNS queries from another terminal.

Remember that cached data can make this experiment inconclusive.

The absence of a root-server packet does not by itself prove that the local root is working because the resolver may already have the required delegation cached.

The authority-zone status and serial number are therefore the more reliable indicators.

# Troubleshooting

Check the configuration:

```bash
unbound-checkconf
```

Check the authority zone:

```bash
unbound-control list_auth_zones
```

Force a transfer:

```bash
unbound-control auth_zone_transfer .
```

Check the zone file:

```bash
ls -lh /var/lib/unbound/root.zone
```

Check the service log:

```bash
journalctl -u unbound --no-pager -n 100
```

If the transfer fails, verify network connectivity to:

```text
192.0.32.132
192.0.47.132
```

If DNSSEC validation fails, do not disable validation just to make the lab work.

A valid local-root implementation must preserve DNSSEC validation.

# Final configuration

The essential Unbound configuration is:

```text
auth-zone:
    name: "."
    master: "192.0.32.132"
    master: "192.0.47.132"
    fallback-enabled: no
    for-downstream: no
    for-upstream: yes
    zonefile: "/var/lib/unbound/root.zone"
```

An authority zone can be maintained by AXFR/IXFR and used as an upstream source for recursive resolution.

# What you have learned

With this configuration Unbound:

1. Maintains a local copy of the root zone.
2. Updates the copy using DNS zone transfers.
3. Uses the local copy for recursive root-zone lookups.
4. Validates the DNSSEC data.
5. Keeps the zone on disk.
6. Does not expose the local root as a normal authoritative service to downstream clients.

The important conceptual difference is:

```text
Root hints
    = where the root servers are

Local root
    = the root zone itself
```

That distinction is the foundation of the local-root mechanism.
